## GitHub 操作の使い分け

- GitHub の情報を **readonly で取得するときは `ghro` コマンドを使う** (issue/PR/コミット一覧、ファイル内容の取得など)
  - ファイル内容を取得するとき Fetch を使わず `ghro api` を使うこと
- 書き込み操作 (issue 作成、PR マージ等) は通常の `gh` コマンドを使う
- `ghro` は書き込み不可のトークンで動くため、書き込みに使わないこと

## Codex CLI 自動委譲ポリシー

- 親は GPT-6.1 Sol / medium を基本とし、要件分析、設計、タスク分解、依存関係の整理、重大な判断、統合と最終品質に責任を持つ。
- Astra はユーザーが明示的に使用を指示した場合だけ使う。この制約は親・子エージェント・フォールバックすべてに適用し、難しい作業や品質不足を理由に自動選択しない。「高品質に」「深く考えて」などの指示だけでは Astra の使用許可とみなさない。
- 独立した十分な作業量のサブタスクは、ネイティブの spawn_agent で以下のカスタムエージェントへ積極的に委譲する。独立した作業は並列化し、子スレッドは最大8（親を除く）とする。
- explorer（Luna / low）: コード探索、関連ファイル・シンボルの特定、既存実装・ドキュメント調査。読み取り専用で作業する。
- worker（GPT-6.1 Sol / medium）: 範囲が明確な実装、バグ修正、リファクタリング、テスト作成。
- reviewer（GPT-6.1 Sol / high）: 独立レビュー、競合状態・メモリ安全性・セキュリティ・回帰・テスト妥当性の検証。読み取り専用で作業する。
- visual_worker（GPT-6.1 Terra / low）: 文章作成・推敲、画像・図表・画面の読み取り、ブラウザ・アプリ操作。実装やコードレビューが主体の仕事は worker / reviewer に任せる。
- lightweight_worker（Luna / low）: 定型修正、機械的変換、小規模で明確な繰り返し作業。
- 軽量モデルで十分なら explorer / lightweight_worker を優先し、通常の実装は worker、文章・視覚情報・画面操作が主体なら visual_worker に任せる。起動コストが作業量を上回る小さな処理は親が直接行う。
- 各委譲には目的、必要最小限の背景、担当ファイルと編集可否、完了条件、必要な検証を明示する。同じファイルを複数の子に同時編集させない。他者の変更を巻き戻させない。
- 依存する作業は先行結果を確認してから実行する。子による再委譲は原則行わず、必要なら親に依頼する。完了した子は適切に終了し、無意味な多段委譲・過剰起動を避ける。
- 品質不足・想定外の複雑さは worker、reviewer、必要なら親へエスカレーションし、Sol の推論強度を上げて対応する。モデルが利用できない場合は失敗を明示し、Astra の使用制約を守り、確認済みの利用可能モデルだけを使う。
- 子の報告は結論、重要なファイルパス、変更内容、実行した検証と結果、未解決事項を簡潔にまとめる。不要な全文転記を避け、親のコンテキスト消費を抑える。
- 親は子の主張を鵜呑みにせず、差分・根拠を確認し、必要なビルド・テストを行ってから成果物を統合する。未検証事項を成功と報告しない。
- 読み取り専用は行動上の制約であり、子のサンドボックス権限は親から継承される。各役割の実際のモデルID・推論強度は ~/.codex/agents/*.toml を正とする。
